# Инструкции для ИИ-агентов

## Начало работы

1. Проверь `git status --short`, `git diff` и `git diff --cached`. Сохрани исходные изменения и границы staged/unstaged; меняй только файлы своей задачи.
2. Определи ожидаемый результат и минимальную проверку до редактирования. Прочитай ближайшую схему, контроллер, маршрут или сервис и соседний пример.
3. При изменении API, моделей, компонентов или конфигурации прочитай [карту проекта](docs/agents/project.md).
4. Перед установкой зависимостей, запуском, сборкой или выбором проверок прочитай [руководство разработки](docs/agents/development.md).

Текущие исходники, `package.json` и `package-lock.json` имеют приоритет над описаниями. Обновляй эти документы, если задача меняет описанный контракт или порядок работы.

## Дисциплина выполнения задач

Работай автономно внутри согласованной задачи.
Не расширяй её ради дополнительных улучшений.

### Границы задачи

- Для нетривиальной задачи до изменений кратко зафиксируй:
  результат, критерии готовности и то, что не входит в задачу.
  Не создавай отдельный документ для этого без необходимости.
- Если существенные требования неоднозначны, сначала уточни их.
  Очевидные локальные технические решения принимай самостоятельно.
- После согласования не пересматривай продуктовые и архитектурные
  решения без новых фактов, показывающих проблему.

### Допустимые изменения

- Меняй только то, что запрошено или необходимо для корректного
  выполнения задачи. Связанные тесты и необходимые исправления
  зависимого кода входят в работу.
- Для каждого изменения должна быть понятна связь с задачей.
  Не добавляй попутный рефакторинг, форматирование соседнего кода,
  новые возможности или абстракции для гипотетического будущего.
- Следуй существующим соглашениям и архитектуре проекта.
- Не меняй публичные контракты, зависимости, схему данных или
  архитектурные границы без согласования, если такие изменения
  не предусмотрены самой задачей.
- Минимальное решение означает минимальную необходимую сложность,
  а не обход причины, отключение проверок или маскировку ошибки.

### Работа с контекстом и находками

- Начинай с относящегося к задаче кода, его связей и тестов.
  Расширяй исследование, когда для этого возникает конкретный вопрос.
  Не проводи общий аудит репозитория без запроса.
- Классифицируй находки:
  CURRENT — необходимо для текущей задачи;
  FOLLOW-UP — полезно отдельно, но сейчас не выполнять;
  IGNORE — несущественно для результата.
- Существенный блокер за пределами задачи объясни и согласуй.
  Не превращай его молча в новую задачу.

### Проверка и завершение

- Проверяй поведение, а не только отсутствие ошибок линтера.
  Для исправления бага добавляй регрессионную проверку, где это уместно.
- Выполняй относящиеся к изменению проверки и обязательные проверки
  проекта. Не исправляй несвязанные старые ошибки без согласования.
- Перед завершением проверь итоговый diff:
  нет ли лишних изменений и не затронута ли чужая незавершённая работа.
- Завершай работу после выполнения согласованных критериев
  и необходимых проверок. Не начинай следующий пункт самостоятельно.
- В итоговом ответе укажи: что сделано, что проверено и что осталось
  непроверенным. Важные FOLLOW-UP перечисли отдельно, без реализации.

## Изменения

- Это сервер Strapi 5 на JavaScript. Используй существующие фабрики Strapi и локальные соглашения; расширяй контроллеры и сервисы только для требуемого поведения.
- Источник моделей — `src/api/*/content-types/*/schema.json`, источник компонентов — `src/components/*/*.json`.
- Сохраняй регистр имён полей, UID моделей и компонентов, `collectionName`, связи и настройки публикации/локализации. Их изменение требует проверки потребителей API и существующих данных.
- Перед изменением схемы определи, что произойдёт с данными и нужна ли миграция. Используй изолированную БД для проверки результата.
- `types/generated/*.d.ts` и `.strapi/client/*` — генерируемые файлы, уже отслеживаемые Git. Не редактируй их вручную. Генерируй типы при необходимости после изменения схем штатной командой установленной версии Strapi; проверь её через CLI help и просмотри весь полученный diff.
- Для настройки админки сначала изучи `src/admin/`; файлы `*.example.js` служат примерами, а `.strapi/client/*` — результатом генерации.
- Соблюдай `.editorconfig` и стиль изменяемого файла. `.eslintrc` существует, но рабочий lint-инструментарий не настроен. Не переформатируй соседний код ради исправления старых расхождений.
- Ограничь изменения необходимыми строками. Добавляй зависимости, абстракции и инструменты только в рамках явно поставленной задачи; существующие `package.json` и lockfile меняй согласованно.

## БД, доступ и внешние системы

- До запуска Strapi проверь целевую БД. Используй выделенную локальную PostgreSQL: запуск приложения может изменять структуру базы.
- `.env`, содержимое БД и `public/uploads/` — локальные данные. Не публикуй секреты, токены, пароли или персональные данные в документах, diff и выводе команд.
- Права публичного API и админки проверяй в нужном окружении. Наличие core router или связи в схеме не доказывает доступность данных для конкретной роли.
- Продакшен, деплой, импорт/экспорт данных, изменение ролей и отправка сообщений требуют соответствующего поручения пользователя. Домен из конфигурации не является разрешением на обращение к живому серверу.
- Коммит, push и изменение индекса выполняй только по поручению пользователя. Сохраняй посторонние изменения, в том числе появившиеся во время проверки.

## Проверка и отчёт

- Проверяй сначала изменённую логику, затем нужную сборку или локальный сценарий. Доступные команды и ограничения описаны в руководстве разработки.
- Изменение API проверяй реальным запросом на локальном сервере с нужной ролью; изменение админки — в Google Chrome на реальном экране. Проверяй относящиеся к задаче пустые, ошибочные и ограниченные правами состояния.
- Проверка синтаксиса и сборка не подтверждают запуск, права доступа или работу UI. Если окружение недоступно, перечисли непроверенные сценарии.
- Перед завершением повторно просмотри рабочее дерево и diff. В кратком отчёте на русском укажи результат, выполненные проверки и существенные ограничения.
